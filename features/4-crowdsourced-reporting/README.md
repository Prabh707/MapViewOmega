# Feature 4: Crowdsourced Reporting

## What this feature does

Riders can flag real-world problems (or good things!) at a stop or on a line directly from the
app — a broken elevator, dim lighting, an unusually crowded platform, a delay, an obstruction, or
even a "this route felt safe" commendation. Those reports feed straight into the **Operator
Dashboard** (feature 5) as a triage queue for the transit operator to act on.

## The data shape: `CommunityReport`

Every report is one object with this shape (`types/transit.ts`):

```ts
export interface CommunityReport {
  id: string;
  stopId?: string;
  stopName: string;
  type: ReportType;          // e.g. 'broken_ramp', 'dim_lighting', 'crowded', 'sos_alert'
  category: ReportCategory;  // e.g. 'Accessibility Barrier', 'Safety Emergency'
  title: string;
  details: string;
  impact: string;            // plain-language explanation of who this affects and how
  timestamp: string;
  upvotes: number;
  status: 'active' | 'in_progress' | 'resolved';
  severity: 'low' | 'medium' | 'high' | 'critical';
  resolvedAt?: string;
  resolutionNote?: string;
}
```

Two fields are worth calling out for a beginner: `type` is the specific, technical tag (useful
for filtering/matching in code), while `category` is the human-friendly grouping shown in the UI.
This separation is a common pattern — it lets you change how something is *displayed* without
touching the underlying logic that depends on the exact `type` value, and vice versa.

## The 8 report types, grouped into 6 categories

| Category | Report types |
|---|---|
| Accessibility Barrier | `broken_ramp`, `escalator_down`, `obstruction` |
| Safety Issue | `dim_lighting` |
| Crowding | `crowded` |
| Transit Delay | `delay` |
| Safety Commendation | `safe_verified` — a *positive* report, for when a corridor felt genuinely safe |
| Safety Emergency | `sos_alert` — tied into Journey Mode's escalation (feature 3) |

## How it works — code walkthrough

Reporting is deliberately simple CRUD, handled entirely in `services/transitService.ts`, which —
remember, this whole app has **no backend** — just keeps an in-memory array as its "database":

```ts
private static reportsCache: CommunityReport[] | null = null;

public static getCommunityReports(): CommunityReport[] { ... }

public static addCommunityReport(
  reportData: Omit<CommunityReport, 'id' | 'timestamp' | 'upvotes' | 'status'>
): CommunityReport[] {
  const newReport: CommunityReport = {
    ...reportData,
    id: /* generated */,
    timestamp: /* now */,
    upvotes: 0,
    status: 'active',
  };
  const updated = [newReport, ...reports];
  // ...
}
```

Notice the `Omit<...>` type on `addCommunityReport` — this is TypeScript enforcing, at compile
time, that whoever calls this function *cannot* supply an `id`, `timestamp`, `upvotes`, or
`status`, because those four fields are always generated by the function itself. That's a nice
beginner-friendly example of using the type system to prevent a whole category of bugs (like a
caller accidentally hardcoding `status: 'resolved'` on a brand-new report).

Two more operations round out the lifecycle:
- `upvoteCommunityReport(reportId)` — lets other riders confirm "yes, I see this too," bumping the
  report's visibility/credibility
- `resolveCommunityReport(reportId, resolutionNote?)` — used by the **operator** (feature 5), not
  the rider, to close out a report once it's been fixed, with an optional note explaining what was
  done

## Why "in-memory" matters here (an important limitation to know)

Because there's no real backend, all of this resets the moment you refresh the page. If you
submit a report, then reload, it's gone. That's completely fine for a demo/prototype, but it's the
single most important thing to understand if you're extending this app: anywhere you see data
that *should* persist (reports, resolved tickets, fleet status changes), it currently doesn't —
you'd need to add a real backend or `localStorage`/`IndexedDB` persistence to change that.
